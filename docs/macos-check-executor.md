# Current macOS check executor

`dist/check/macos-isolation.js` is the bundled trusted executor for the Journeys hash-pinned deployment boundary. It supports the actual current macOS arm64 host, `macos-arm64` or its `server` target, thin arm64 Mach-O entries and SDK-routed networking. An executor cannot accept another claim target. Direct network asks, other architectures, universal executables and unavailable kernel confinement refuse before uploaded code starts. This is implementation for the existing installed-build check, with other-target and normal installed acceptance still separate.

The parent retains platform identity, model routing, account-save and signing authority. The child receives only a fresh private HOME/TMPDIR, the one-use SDK connection and check marker. The kernel profile permits read-only access to the exact materialized tree, system frameworks/runtime/ICU, the root directory itself and random/null devices. Only private scratch and null-device writes are allowed. Only TCP to the selected loopback SDK port is allowed. Other Mach service lookups, host file reads, process creation/execution, signals to other processes, public and metadata networking remain denied. Process-information operations require an explicit denial because macOS does not include every operation in deny-default; the self-only exception cannot read the parent's arguments or environment.

The actual compiled adversarial probe verifies successful private scratch and SDK TCP access, plus denied host-canary and symlink reads, immutable-tree and outside writes, other loopback/public/metadata TCP, parent signaling, parent `KERN_PROCARGS2`, fork and another executable. The target guard independently refuses an x64 header and a different claim target. These are kernel enforcement observations on the current host, with synthetic canaries and no credential values.

`sandbox-exec` is deprecated by macOS. The executor checks its actual presence and a real kernel launch before accepting work, and has no ordinary subprocess fallback. Current proof does not guarantee future macOS compatibility or establish complete security analysis. The existing static findings, sampled socket limits, fixed duration, immutable materialization and signing prerequisites still apply.

## Window-capable sample

`scripts/build-native-window.mjs OUTPUT VERSION` embeds the unchanged SDK and Kestrel core in the same Mach-O program as a small AppKit presentation. A headless grant does not create native controls or a window. Normal installed grants display the game and its assignment, advance and save controls. The program reads its guide through the SDK, loads exact account state and uses the core's ordinary save handlers. The two packaging variants change a visible release label while preserving save compatibility. Each variant requires its own complete check, signature and exact static occurrence record. No metadata interpretation is inherited from another artifact hash, target or path.

The checked program is launched through the existing native installer/receipt verification and SDK transport. A generated memory-only fixture trust can prove that composition; ordinary installed App acceptance requires the actual approved GSM signing key, matching compiled public trust and configured checker identity. No key, IAM role or service configuration is activated by this implementation.
