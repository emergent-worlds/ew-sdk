# Local installed-build checks

`@emergent-worlds/sdk/check` supplies `runBuildCheck(plan, services, signal?)` for one declared target. It is Node 24 tooling. The ordinary SDK entry does not load the check runner, socket server, or process tools. The check subpath bundles its local WebSocket dependency; it adds no runtime dependency to the ordinary SDK binding.

This implements the local portion of E17, MR3.4, and the six checks in S8. The platform still owns the queue, check account, isolated job or native check runner, immutable input tree, model catalogue, model route, signing service, and publication gate. The runner has no cloud credentials or signing key. It does not dispatch jobs or sign by itself.

## Inputs and outputs

The plan names the immutable folder and version, target, manifest, laid-out root, complete file tree, actual executable path, and current provider hostnames from the model catalogue. Each file has a canonical relative path, SHA-256, byte size, and executable flag. The tree includes files outside the selected build prefix so the executable scan can inspect them. The manifest's `entry.installs[target]` is the build prefix; `entryPath` names the executable under it, including the executable inside a macOS bundle. The platform resolves that path rather than guessing it from an extension.

The runner validates the manifest with ew-host, verifies that it matches `manifest.json` in the immutable tree, checks at most 10,000 files, rejects traversal, links, escaping paths, normalized duplicate paths and case collisions, and verifies actual sizes, hashes and executable modes before launch. It streams the scan rather than loading a whole build into memory. An executable found by mode or a native executable header outside the prefix fails the scan. Archive extensions and common archive headers are reported, including archives renamed to ordinary data files. These are bounded scans, not a complete executable or archive classifier.

The result contains six rows, in the record's order, with a result and evidence. It reports `passed` only when all six rows pass. The sixth row stays pending when a prerequisite fails or signing integration is absent. Its sign callback receives folder, version, target, and the target's verified files. The integration owns the versioned canonical signed file-list encoding and builds key; it must return the actual signature and the canonical file-list SHA-256. An absent or incomplete acknowledgment cannot produce a signing pass. The callback is never called before the other five rows and both executable/archive scans pass. This structural input is not a replacement for ew-host's eventual canonical signed file-list schema.

## The run

The runner opens an ephemeral listener on `127.0.0.1`, creates a 32-byte launch token in memory, and starts only the checked executable, with `EW_SDK_CHECK=1` and the SDK connection in its environment. The child receives a small operating-system environment allowlist, without copying arbitrary parent environment variables or provider credentials. It accepts one token-bearing first frame within 30 seconds. Later frames use the ordinary core bridge and manifest asks, with a 4 MiB frame bound. The token is not included in evidence, a URL, or logs; child output is discarded.

After admission it observes a full 60 seconds. The duration is fixed; cancellation, early process exit, lost connection, a missing SDK socket observation, failed sampling, and a refused message prevent passing evidence. It then asks for an interval save through the game's ordinary handler and the required `save` service, awaits that service's version acknowledgment, requests quit, and verifies that another acknowledged leaving save occurred during quit. Cancellation also closes the bridge during save or quit, rejecting those pending requests immediately. The launcher owns process termination after acknowledgment. Cleanup closes sockets, stops timers, terminates the child, and eventually forces termination if necessary. The platform integration remains responsible for cancelling its in-flight storage or signing operation and rejecting a result whose queue claim has expired.

The required `save` service must call the check account's platform route. A memory callback used by a local fixture proves the callback and game lifecycle, not account persistence in a deployed environment. Model calls are delegated to the supplied platform route and their jobs and failed routes are recorded. The runner never makes a direct provider call.

## Static and network evidence

The static scan records literal HTTP/WebSocket hosts, IPv4 addresses and common domain suffixes in build bytes. Provider hostnames are compared with the supplied catalogue; other hosts are compared exactly with the manifest's network ask, with an optional explicit port. Embedded metadata is not silently exempted. A packaged runtime may therefore need review when its metadata contains network literals. Static scanning cannot discover every constructed or encoded address, domain suffix, or provider route.

Every 250 ms the runner samples TCP endpoints of the launched process. On Linux it filters `/proc/<pid>/net/tcp` and `tcp6` by socket inodes owned through that process's file descriptors. On current macOS it filters `netstat -anv -p tcp` by `process:pid`; on Windows it filters `netstat -ano -p tcp` by PID. It records all observed endpoints, denied endpoints, successful SDK observations, sample failures, and missed intervals. Only the check's SDK endpoint is implicitly permitted; other connections must match the network ask. Declared hostnames are resolved once before launch so their IP endpoints can be compared without dropping explicit port restrictions. DNS changes during a run are not tracked; a newly resolved address can therefore require another check.

These observations do not cover descendants, operating-system helper processes, UDP, connections shorter than a sampling interval, or activity outside the run. A missing SDK observation fails rather than presenting an empty parser result as proof. An unsupported netstat format or operating system cannot produce a pass. This is not a sandbox or a security guarantee. The deeper security work remains separate, as the approved record requires.

## Verification

`pnpm test` covers ordering, missing evidence, prerequisite gates, signature acknowledgment, hashes, modes, actual manifest consistency, static provider and network literals, disguised archives and executables, path/link refusal, process ownership in socket parsers, and a real local socket on the current operating system. POSIX child fixtures also verify arbitrary parent environment filtering, cancellation, wrong-token refusal, and token consumption; those shebang-based fixtures are skipped on Windows until a Windows executable fixture exists.

`pnpm check:runner` runs the complete 60-second lifecycle against the real Kestrel Yards core. Its temporary executable imports the locally built sample through an explicit external local path. The fixture checks actual state saves with synthetic storage and no signing callback; the first five rows are expected to pass and the sixth to remain pending. `node scripts/check-runner.mjs cancel-save` repeats the full observation, cancels when the save service is entered, and verifies that no save acknowledgment or signing pass is invented. Diagnostic output preserves network evidence when a run fails, including missed intervals on a busy machine. This fixture is not a self-contained install target, a platform account-persistence test, or artifact acceptance. Real declared target checks must use their complete staged trees and platform services. Windows and Linux native samplers, deployed queue integration, isolated runners, canonical signing integration, and publication acceptance remain open until exercised.
